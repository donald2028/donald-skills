# Donald Agent Infrastructure

## Overview

Use this skill to give a project a durable agent-led skill management layer. The core pattern is:
one canonical project contract, one canonical skill source, generated runtime adapters, and
optional routing, governance, and subagent layers.

This skill is intentionally broader than one Donald product. It supports lightweight projects
with a few flat skills, categorized product systems with many internal skills, and projects that
also need generated Claude/Codex subagents.

## First Pass

1. Read the target repo's `AGENTS.md`, `CLAUDE.md`, `CODEBUDDY.md`, `skills/`,
   `.claude/skills/`, `.agents/skills/`, `.codebuddy/skills/`, `.kimi-code/skills/`, legacy
   `.kimi/skills/`, `.codex/agents/`, and `agents/` if they exist. Inventory any other runtime
   directories the project already uses.
2. Classify the project into the smallest profile that fits:
   - `minimal`: canonical `AGENTS.md`, Claude/CodeBuddy adapters, and a few flat skills.
   - `categorized`: organized `skills/<category>/<skill>/SKILL.md` source plus generated mirrors.
   - `pipeline`: the categorized profile plus an entry skill for genuine cross-skill routing.
   - `subagents`: the pipeline profile plus generated runtime-specific subagent files.
3. Decide separately whether the project needs the optional governance layer. Do not add an entry
   skill merely because skills are categorized, or governance merely because an entry skill exists.
4. Preserve user changes. During migration, treat existing runtime mirrors and generated folders as potentially
   hand-edited until the sync script proves otherwise.
5. If the user only asked for a plan, return the migration plan and stop before writing files.

Read `references/architecture.md` when designing a new project structure or generalizing an
existing one. Read `references/migration.md` before changing an existing repo.

## Initialize Or Migrate

Use `scripts/init_project_agent_infra.py` for safe scaffolding. It writes only missing files
unless `--force` is passed.

Run it against the target repo with the project name and profile. Add `--with-governance` only when
the project needs a project-local review skill and audit script. Exact validation commands live in
`references/internal-runtime.md`.

All profiles generate a sync helper targeting `.claude/skills/`, `.agents/skills/`, and
`.codebuddy/skills/`. Kimi Code and OpenCode reuse `.agents/skills/`; WorkBuddy uses the
CodeBuddy Code adapter. Read `references/architecture.md` for runtime mappings and extensions.
The initializer only writes scaffolding: run the generated sync helper to create the mirrors.

Use `--with-subagents` only when the project needs isolated worker/reviewer roles that should
exist consistently in multiple runtimes.

After initialization, edit the generated project contract and entry skill so they name the
project's real modes, red lines, runtime observations, and skill families. Do not leave generic
placeholder capability claims in a project contract.

## Audit

Use `scripts/audit_project_skills.py` for a repo-independent skill quality report:

Point it at the target repo's canonical `skills/` root. Use `--strict` when recommended authoring
limits should be enforced in addition to baseline format checks.

Run the target repo's generated `skills/sync_runtime_skills.py --check` after any add, rename,
remove, or move under canonical `skills/`.

## Core Contract

Enforce these rules across profiles:

- `AGENTS.md` is the canonical cross-runtime project contract. `CLAUDE.md` is a thin Claude adapter
  and `CODEBUDDY.md` is a thin WorkBuddy/CodeBuddy adapter; keep only runtime-specific additions there.
- `skills/` is the canonical source for project-local skills.
- `.claude/skills/`, `.agents/skills/`, and `.codebuddy/skills/` are disposable runtime mirrors
  generated by script. Kimi Code uses the shared `AGENTS.md` and `.agents/skills/` directly.
- Runtime commands, flags, schemas, and fragile recipes live in `references/`, not in the main
  user-facing chat answer.
- A skill requires only `SKILL.md`. Add `references/`, `scripts/`, `assets/`, `evals/`, or
  `agents/openai.yaml` only when the workflow actually needs them.
- Every project should have one entry skill when requests need routing, capability inventory,
  user/builder modes, or domain-specific red lines.
- Project subagents, when used, are declared once in `agents/registry.yaml`; generated runtime
  files are never hand-edited. The bundled subagent generator targets only Claude/Codex;
  WorkBuddy/Kimi skill support does not imply subagent format support.
- Audit scripts produce observations. The main agent still owns semantic judgment.
